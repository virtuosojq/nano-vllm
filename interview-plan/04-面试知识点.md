## 第 1 章 LLM 推理基础

### 1.1 prefill 和 decode

| | prefill | decode |
|---|---|---|
| 输入 | 整个 prompt（N 个 token） | 1 个 token（上一步输出） |
| 计算形式 | 矩阵乘矩阵（GEMM） | 矩阵乘向量（GEMV），批起来才变回 GEMM |
| 瓶颈 | 计算（算力） | 访存（显存带宽） |
| 算术强度 | 高 | 极低（批大小为 1 时约等于 1） |
| 指标 | TTFT | TPOT、ITL |

**为什么 decode 是访存瓶颈**：每生成一个 token，都要把全部模型权重从显存读一遍，但只做很少的计算。batch size 为 1 时，每读一个权重字节只做约 2 次浮点运算，而现代加速卡的算力/带宽比远高于这个值，所以时间全花在搬数据上。

**推论（面试常考）**：

- decode 阶段把 batch 做大几乎不增加时间，因为权重只读一次，被所有序列摊薄。这是 continuous batching 有效的根本原因。
- 投机解码能工作，也是因为一次验证 k 个 token 和算 1 个 token 的耗时接近。
- 权重量化（W8A8、W4A16）对 decode 收益大，因为直接减少了要搬的字节数。
- decode 的时间下限 ≈ 权重字节数 / 显存带宽。实测和下限的比值就是带宽利用率。

### 1.2 KV cache 大小

```
每 token 字节数 = 2（K 和 V）× 层数 × KV 头数 × head_dim × dtype 字节数
```

例：Qwen3-30B-A3B，48 层、4 个 KV 头、head_dim 128、BF16：
`2 × 48 × 4 × 128 × 2 = 98,304 字节 ≈ 96KB/token`

要能当场算，并由此推出「这张卡能放多少 token、能撑多少并发」。

### 1.3 MHA / MQA / GQA / MLA

| | KV 头数 | KV cache | 说明 |
|---|---|---|---|
| MHA | = Q 头数 | 最大 | 原始 Transformer |
| MQA | 1 | 最小 | 所有 Q 头共享一组 KV，质量有损失 |
| GQA | 分组，每组共享 | 折中 | 现在主流（Llama、Qwen） |
| MLA | 低秩压缩 | 很小 | DeepSeek；把 KV 压成低维隐向量存储，用时再升维 |

MLA 的要点：存的是压缩后的隐向量，显著减小 KV cache；代价是多了升降维计算，而且可以用矩阵吸收把部分计算合并掉。

## 第 2 章 Attention 优化

### 2.1 FlashAttention

**解决什么**：标准实现要物化 `N×N` 的注意力矩阵，显存占用和读写量都是 `O(N²)`，而这个矩阵的读写才是真正的瓶颈。

**怎么做**：分块（tiling）计算，Q 分块、KV 分块，在片上内存里完成局部的 softmax 和加权求和，不把完整矩阵写回显存。关键技术是 **online softmax**：边扫边更新最大值和归一化分母，用缩放因子修正之前的部分结果，保证数值稳定且只需一趟。

**效果**：显存从 `O(N²)` 降到 `O(N)`，HBM 读写量大幅减少，是 IO 感知的优化而不是减少计算量。

**要会写**：online softmax 的更新公式（见 `05` 的手写题单）。

### 2.2 FlashDecoding

decode 时 Q 只有 1 个 token，按 Q 分块的并行度严重不足，GPU 大量空闲。FlashDecoding 改为**沿 KV 长度切分**，多个块并行算出部分结果，最后用 online softmax 的方式合并（rescale 后相加）。长上下文的 decode 收益明显。

### 2.3 PagedAttention

**解决什么**：KV cache 按最大长度预分配会造成大量内部碎片，不同请求之间无法共享。

**怎么做**：借鉴操作系统的分页，把 KV cache 切成固定大小的块，逻辑上连续的序列在物理上可以不连续，用 block table 做映射。attention kernel 按 block table 去取。

**带来的能力**：按需分配（碎片小）、前缀共享（相同前缀的块引用同一份物理块）、写时复制、抢占后重算。

**块大小的权衡**：小块碎片少、前缀命中粒度细，但 block table 更长、kernel 访问更零散；大块反之。vLLM 默认 16，nano-vllm 用 256。

## 第 3 章 调度与批处理

### 3.1 continuous batching

静态批要等整批里最慢的请求结束，GPU 大量空转。连续批（也叫 in-flight batching）以「步」为单位调度：每步结束后，完成的请求立刻离开，等待中的请求立刻补进来。

### 3.2 chunked prefill

**解决什么**：一个长 prompt 的 prefill 会独占一步，这一步里所有正在 decode 的请求都被卡住，表现为 ITL 出现尖刺。

**怎么做**：给每步设 token 预算，长 prefill 被切成多块，分散到多步；同一步里可以既有 decode 又有 prefill 分块。

**权衡**：预算小则 ITL 平稳但 TTFT 变高；预算大则反之。这正是项目 A 里 token_budget 和 hybrid 两个策略要讲的内容。

vLLM V1 的做法更彻底：不再区分 prefill 步和 decode 步，每个请求只有「已算了多少 token」，调度器每步决定给谁算多少个。

### 3.3 prefix caching

相同前缀（system prompt、few-shot 示例、多轮对话历史）的 KV 可以复用。实现方式是对每个满块算哈希（内容 + 父块哈希，形成链），命中则直接引用，跳过这部分 prefill。

**注意**：只缓存满块；引用计数归零的块进 LRU 空闲队列，被重新命中时可以复活。

### 3.4 抢占

显存不够时，要从正在跑的请求里挑一个让出 KV。两种恢复方式：

- **重算**：丢掉 KV，恢复时重新 prefill。实现简单，而且 prefill 本来就快。vLLM V1 用这个。
- **换出（swap）**：KV 搬到 CPU 内存，恢复时搬回。省了重算，但 PCIe 带宽经常成为新瓶颈。

### 3.5 PD 分离

prefill 是计算瓶颈、decode 是访存瓶颈，混在一起会互相干扰，而且两者适合的并行策略和硬件配置也不同。PD 分离把它们放到不同实例上，prefill 完成后把 KV 传给 decode 实例。

**代价**：KV 传输（走 RDMA / HCCS）；需要路由和调度层配合。

**相关**：cache-aware 路由（把有相同前缀的请求路由到同一个实例，提高命中率）。

## 第 4 章 投机解码

### 4.1 为什么有效

decode 是访存瓶颈，一次前向验证 k 个 token 和算 1 个 token 的时间接近。所以用便宜的方式猜 k 个，再用大模型一次性验证，猜中就白赚。

### 4.2 几种方法

| 方法 | draft 来源 | 成本 | 适用场景 |
|---|---|---|---|
| draft model | 小模型 | 要额外跑一个模型 | 通用 |
| n-gram / prompt lookup | 从 prompt 和已生成内容里找重复片段 | 几乎为零 | 代码补全、文档编辑、摘要等重复多的场景 |
| EAGLE / EAGLE3 | 轻量 draft 头，基于大模型的隐状态预测 | 小 | 通用，接受率高 |
| MTP | 模型自带的多 token 预测头 | 小 | 模型原生支持时（DeepSeek） |
| Medusa | 多个预测头 + 树形验证 | 小 | — |

### 4.3 正确性

**拒绝采样**保证输出分布和不投机完全一致：按 `min(1, p_target/p_draft)` 的概率接受，拒绝时从修正后的分布重采样。贪心时退化成「逐个比对，不一致就截断」。

所以投机解码是**无损**的。实际工程中可能因为批形状不同带来浮点误差，在长序列后分叉，要能解释清楚这个现象。

### 4.4 代价与边界

- 接受率低时，draft 的开销白费，反而变慢。
- 并发高时，decode 已经接近计算瓶颈，验证 k 个 token 不再免费，收益下降甚至为负。
- 调度器要为 draft token 预留 KV slot；被拒绝的 token 占用的 slot 要回收。

### 4.5 常见追问

- 接受率多少才划算？怎么估算盈亏平衡点？
- 并发多大时投机解码会变成负收益？为什么？
- 怎么证明投机解码是无损的？

## 第 5 章 量化

### 5.1 按量化对象分

| 方案 | 权重 | 激活 | KV | 主要收益 |
|---|---|---|---|---|
| W8A16 / W4A16 | INT8 / INT4 | 保持高精度 | — | decode 访存（权重搬运减少） |
| W8A8 | INT8 | INT8 | — | 访存 + 计算（能用 INT8 算力） |
| FP8（E4M3） | FP8 | FP8 | 可选 | 同上，动态范围比 INT8 好 |
| KV cache 量化 | — | — | INT8 / FP8 | KV 容量翻倍，能支持更大并发或更长上下文 |

### 5.2 静态与动态

- **静态量化**：scale 离线标定好，推理时直接用。快，但对分布变化敏感。
- **动态量化**：scale 在推理时按当前输入算。精度好，但每次都要多算一遍。

Qwen3-30B-A3B-W8A8 的做法就是混合：attention 投影用静态（per-tensor 预计算 scale），MoE 专家用动态（运行时算 scale）。这是一个很好的面试素材。

### 5.3 粒度与算法

- 粒度：per-tensor < per-channel < per-group（如 128）< per-token。越细越准，开销越大。
- 算法：GPTQ（逐层最小化输出误差）、AWQ（按激活幅度保护重要通道）、SmoothQuant（把激活的难度迁移一部分到权重上）。

### 5.4 KV cache 量化

项目 A 里做过 INT8 KV：写入时量化、读取前反量化。要能讲：

- 容量收益（你的旧结果是块数约 ×1.78）
- 额外的反量化计算开销
- 精度怎么验证（用 GSM8K 等下游任务，不能用逐 token 对齐）
- per-token 还是 per-tensor 的 scale，scale 存在哪

### 5.5 常见追问

- 为什么 decode 场景权重量化收益最大？
- INT8 和 FP8 哪个更适合激活量化？为什么？
- MoE 模型量化有什么特殊之处？（专家多、每个专家被激活的频率不同）

## 第 6 章 并行与分布式

### 6.1 四种并行

| 并行 | 切什么 | 通信 | 适用 |
|---|---|---|---|
| TP（张量并行） | 每层的权重矩阵 | 每层 2 次 all-reduce（attention 后、FFN 后） | 单卡放不下；通信频繁，要求卡间带宽高 |
| PP（流水线并行） | 按层切 | 层间传激活（点对点） | 跨节点；有气泡，推理中用得少 |
| DP（数据并行） | 不切模型，多副本 | 无（或少量） | 吞吐扩展 |
| EP（专家并行） | MoE 的专家分到不同卡 | dispatch + combine（all-to-all） | MoE 模型 |

### 6.2 TP 的细节

- `ColumnParallelLinear`：按输出维切，各卡算各自的一部分，结果需要 all-gather 或直接接下一层。
- `RowParallelLinear`：按输入维切，各卡算部分和，需要 all-reduce。
- 一层 Transformer（attention + FFN）共需 2 次 all-reduce。
- 注意力头数必须能被 TP 数整除；GQA 时 KV 头数也要能整除，否则要复制。

### 6.3 MoE 与 EP

- 路由：gate 给每个 token 选 top-k 个专家。
- dispatch：把 token 发到对应专家所在的卡（all-to-all）。
- combine：把结果收回来（all-to-all）。
- 通信量和 token 数、hidden size、top-k 有关。
- **负载不均**：热门专家所在的卡成为瓶颈。解决办法有 aux loss（训练时）、EPLB（推理时做冗余专家和重分布）。

### 6.4 DP attention + EP

MLA 模型（DeepSeek）里，attention 部分 TP 切不动（KV 头少），于是 attention 用 DP（每张卡处理不同的请求），MoE 部分用 EP。这样 KV cache 不重复、专家分散。

### 6.5 常见追问

- 为什么推理里 PP 用得比训练少？

- EP 下怎么处理专家负载不均？

## 第 7 章 昇腾专项

这一章是你的主场，但要能用「让 GPU 背景的面试官听懂」的方式讲。

### 7.1 硬件

- **达芬奇架构**：AI Core 内部有 Cube 单元（矩阵乘）、Vector 单元（逐元素、归约）、Scalar 单元。CANN 算子开发就是在编排这三者和各级片上缓冲。
- **A3（910C）**：一台 8 卡，**双 die 设计**，系统里看到 16 个 `/dev/davinci*`。每个 die 有独立显存。
- **互联**：die 间和卡间走 HCCS；跨节点走 RoCE。HCCL 是对应的集合通信库，地位类似 NCCL。

### 7.2 软件栈

```
vLLM（引擎、调度、KV 管理）
  └─ vllm-ascend（平台插件：worker、model runner、attention、MoE、图模式）
       └─ torch_npu（PyTorch 的昇腾后端；op-plugin 做算子注册和适配）
            └─ CANN（AscendCL 运行时、aclnn 算子库、HCCL）
                 └─ 固件 / 驱动 / NPU
```

你的 `ops-transformer` 工作在最底层（CANN 算子），项目 B 要做的就是把上面几层串起来。

### 7.3 ND 与 NZ

昇腾的 Cube 单元对数据排布敏感。ND 是常规排布，NZ 是分形排布（更贴合 Cube 的读取方式）。权重转成 NZ 可以提升 matmul 效率，代价是转换开销和显存布局变化。vllm-ascend 用 `--additional-config '{"weight_nz_mode": 2}'` 控制。

### 7.4 图模式（ACL Graph）

和 CUDA Graph 目的相同：把一串 kernel 下发录制成一张图，重放时省掉 host 侧逐个下发的开销。对小 batch 的 decode 收益最大，因为那时 host 下发开销占比高。

昇腾特有的点（见本地 `ACL_Graph.md`）：

- vLLM 提供通用的调度和分桶，vllm-ascend 提供 `ACLGraphWrapper` 做捕获和重放。
- 捕获尺寸受 runtime 资源限制，可能比 vLLM 配置的更少。
- 整图重放时，attention 的参数要在 host 侧更新（因为每步的序列长度和 block table 在变）。
- piecewise（把 attention 留在图外）和 full（整图）两种模式；`FULL_DECODE_ONLY` 表示只给 decode 用整图，prefill 走 eager，是常用选择。

### 7.5 MC2

**是什么**：把计算和通信融合进同一个算子（Matmul + Communication 的融合，对应 `ops-transformer/mc2/` 下的算子），减少 host 介入和同步点，让通信和计算在片上重叠。

**在 MoE 里**：`npu_moe_distribute_dispatch_v2` 和 `npu_moe_distribute_combine_v2` 把专家间的 all-to-all 和相关计算融合。vllm-ascend 还有 FUSED_MC2，把 dispatch、FFN、combine 进一步融成一个算子。

**限制**：有 token 容量上限（`mc2_tokens_capacity`）；要求各 rank 的 token 数一致。所以 token 多的 prefill 场景可能回退到 ALLTOALL。

**面试讲法**：「在昇腾上，MoE 的专家通信有三条路径。不开 EP 时用 AllGather；开了 EP 后，token 多时用 AlltoAll，token 少的 decode 场景用 MC2，因为 MC2 把通信和计算融进一个算子，省掉了 host 同步，对延迟敏感的 decode 更有利，但它有 token 容量上限。」

## 第 8 章 服务化与工程

### 8.1 指标

TTFT、TPOT、ITL、E2EL、吞吐（req/s、output tok/s、total tok/s）、goodput。定义见 `01-项目A-评测重做.md` 末尾。

### 8.2 SLO 与容量规划

典型 SLO：TTFT < 1s（对话）、TPOT < 50ms（比人阅读速度快）。

容量规划的思路：

1. 从 SLO 反推单实例能承载的并发。
2. 用 Little 定律：系统中的请求数 = 到达率 × 平均延迟。
3. 算 KV cache 容量能支持多少并发，和算力能支持多少并发，取小的那个。
4. 加上峰值系数和冗余。

### 8.3 其他

- **压测方法**：开环（request-rate）vs 闭环（max-concurrency）；泊松到达；为什么要 warmup 和重复。
- **路由**：轮询、最少连接、cache-aware（前缀亲和）。
- **结构化输出**：xgrammar / outlines，用 FSM 约束 logits；对性能的影响。
- **多 LoRA**：一个基座模型服务多个 LoRA，权重合并与分离的权衡。
