基于 `back` 分支 `baseline.py` 和 `nanovllm/engine/metrics.py`，按严重程度排序。面试时如果被问到「你之前是怎么测的」，这些就是你主动反思的素材。

| # | 问题 | 代码位置 | 后果 |
|---|---|---|---|
| 1 | 在引擎进程内、`step()` 之后打点；vLLM 在客户端测，包含分词、反分词、HTTP、流式返回 | `run_workload`、`suite_serving` | 和 vLLM 的数字不能直接比 |

| 8 | 只测 Qwen3-0.6B | `DEFAULT_MODEL` | 小模型的 CPU 和调度开销占比高，结论不一定能推到大模型 |

## 四、OpenAI 兼容服务设计

新增文件建议：`bench/nano_server.py`（服务）、`bench/fake_engine.py`（本地测协议用）、`bench/run_matrix.sh`（总控）、`tools/collect_env.py`。

### 架构

```
HTTP 请求 ──► FastAPI (asyncio 事件循环)
                │  分词、构造 SamplingParams、建一个 asyncio.Queue
                ▼
          request_queue (线程安全) ──► 引擎线程：循环
                                         1. 取出所有新请求 → engine.add_request
                                         2. engine.step()
                                         3. 对每个 running / finished 的序列，算出新增的 token
                                         4. 通过 loop.call_soon_threadsafe 把增量推回各自的 Queue
                ◄────────────────────────┘
          增量反分词 → SSE 推给客户端
```

要点：

- **只有引擎线程调用 `engine.*`**。HTTP 侧只往 `request_queue` 里放东西，避免和调度器并发访问。
- 引擎空闲时阻塞在 `request_queue.get()` 上，不要空转。
- 新请求的到达时刻在 HTTP 处理函数入口记录，这样服务端内部指标也包含排队和注入等待。
- 每步都要推增量，不能攒到请求结束再推，否则客户端测出来的 TTFT 和 ITL 都是错的。
- 当前 `engine.step()` 只在结束时返回 `(seq_id, token_ids)`。流式需要你自己维护 `seq_id → 已推送 token 数`，每步之后扫一遍 `scheduler.running` 和本步结束的序列，取新增部分。旧 `suite_serving` 里已经有类似逻辑，可以复用。
- 请求和 `seq_id` 的对应关系：`add_request` 之后从 `scheduler.waiting[-1].seq_id` 拿（旧代码就是这样），或者改 `add_request` 让它返回 `seq_id`，后者更干净。

### 接口规格

| 接口 | 用途 | 必须支持的字段 |
|---|---|---|
| `POST /v1/completions` | 压测和精度评测都走这里 | `model`、`prompt`（字符串；可选支持 token id 列表）、`max_tokens`、`temperature`、`stream`、`stream_options.include_usage`、`ignore_eos`、`stop`（字符串或列表） |
| `GET /v1/models` | 客户端探活、取模型名 | 返回 `--served-model-name` |
| `GET /health` | 总控脚本等服务就绪 | 200 |
| `GET /nano/metrics` | 诊断层 | 返回 `engine.get_metrics()` |
| `POST /nano/reset_metrics` | 每个场景开始前清零 | — |

`top_p`、`top_k` 这类字段 nano-vllm 不支持，收到时直接忽略即可；`vllm bench serve` 默认 `temperature=0`，就是贪心。

### 流式返回格式

```text
data: {"id":"cmpl-1","object":"text_completion","created":1731000000,"model":"Qwen3-4B","choices":[{"index":0,"text":" Paris","finish_reason":null}]}

data: {"id":"cmpl-1","object":"text_completion","created":1731000000,"model":"Qwen3-4B","choices":[{"index":0,"text":".","finish_reason":"length"}]}

data: {"id":"cmpl-1","object":"text_completion","created":1731000000,"model":"Qwen3-4B","choices":[],"usage":{"prompt_tokens":5,"completion_tokens":2,"total_tokens":7}}

data: [DONE]

```

- 最后一个带 `usage` 的 chunk 很重要：压测客户端优先用 `usage.completion_tokens` 统计输出长度，没有的话会对生成文本重新分词，可能和真实 token 数有偏差。
- `finish_reason`：达到 `max_tokens` 为 `length`，遇到 EOS 或 `stop` 为 `stop`。
- 非流式时返回一个完整 JSON，`choices[0].text` 为全部文本，带 `usage`。

### 实现中的坑

1. **增量反分词**：逐 token 单独 decode 会把多字节字符切坏。用「整段 decode 后取新增后缀」的方式，或者参考 vLLM 的 incremental detokenizer 思路。
2. **`stop` 字符串**：lm-eval 跑 GSM8K 时会传 `stop`（如 `"Question:"`）。服务端要在输出文本里检测到 stop 后截断、标记结束，并**通知引擎提前终止这个序列**，否则会白白生成到 `max_tokens`，精度评测也会变慢。
3. **投机解码时一步出多个 token**：一个 chunk 里放多个 token 的文本即可，vLLM 也是这样；ITL 的含义会变成「chunk 间隔」，报告里注明。
4. **`max_model_len` 截断**：prompt + `max_tokens` 超过上限时返回 400，不要静默截断，否则两侧的负载不一致。
5. **客户端断开**：流式请求中途断开时要把序列从调度器里移除，否则 KV 一直占着。

### 本地验证（不需要 GPU）

1. `fake_engine.py` 实现同样的 `add_request / step / is_finished` 接口，每步给每个序列吐一个固定 token，带可配置的 sleep 模拟步耗时。
2. 用 `curl -N` 测流式；用 `openai` Python SDK 测非流式。
3. 在本地 `vllm` 环境里装 vLLM（只用客户端），对假服务跑一次 `vllm bench serve --num-prompts 20`，确认能正常出结果文件。
4. 用假服务跑一次 lm-eval 的 `--limit 5`，确认 `stop` 生效。

## 八、每项优化重测后怎么讲

数字在重测后填。每项准备「做了什么 → 在哪个场景看效果 → 为什么 → 代价」四句话。

| 优化 | 主要场景 | 预期现象 | 要准备的解释 |
|---|---|---|---|
| 原版 prefill 优先 | S3、S5 | 有新请求时 decode 被整步打断，ITL p99 高 | prefill 和 decode 不能在同一步混跑，长 prefill 独占一步 |
| token_budget | S3、S5 | ITL p99 降，TTFT 升 | 限制每步 prefill token 数，用 TTFT 换 ITL |
| hybrid（同一步混 batch） | S3、S5 | ITL p99 和 TTFT 同时改善，goodput 提高 | 和 vLLM chunked prefill 的思路一致：decode 优先占预算，剩余预算给 prefill 分块 |
| decode pack（常驻 pinned buffer） | S2 | 很可能在噪声范围内 | CPU 侧准备输入的开销在 4B 模型上占比很小；**诚实报告「没有可测收益」** |
| n-gram 投机 | S6 | 并发 1 时 TPOT 明显下降，并发升高后收益消失甚至变慢 | decode 是访存瓶颈，验证 k 个 token 和算 1 个成本接近；并发高时已接近计算瓶颈，验证的额外计算不再免费 |
| INT8 KV | S2、高并发的 S3 | KV block 数约 ×1.78（旧结果），可同时运行的序列更多，饱和吞吐提高 | KV 容量决定最大批大小；反量化有额外计算；精度用 GSM8K 证明 |

和 vLLM 的对比要能回答：「nano-vllm 优化后在哪些场景接近 vLLM、哪些场景差得远、差在哪里」。差距本身不丢人，能解释原因才是重点（比如 vLLM 有更成熟的 attention backend、更细的 CUDA Graph 分桶、异步调度、更小的 block 粒度）。

## 本阶段要掌握的知识点

面试中问到「你怎么测的」时，下面每一条都要能讲清楚。

**指标定义（和 vLLM 一致）**

- **TTFT**：从客户端发出请求到收到第一个 token 的时间。包含排队、prefill、首个 token 的网络返回。
- **TPOT**：`(E2E 延迟 − TTFT) / (输出 token 数 − 1)`，即首 token 之后平均每个 token 的时间。
- **ITL**：相邻两次流式返回之间的时间间隔。TPOT 是请求内平均，ITL 是所有间隔的分布；ITL 的 p99 更能反映卡顿。
- **E2EL**：请求的端到端延迟。
- **吞吐**：req/s、output tok/s、total tok/s（输入 + 输出）。说吞吐时必须说清是哪一个。
- **goodput**：每秒满足 SLO（比如 TTFT ≤ 500ms 且 TPOT ≤ 50ms）的请求数。比单纯的吞吐更接近业务价值。

**压测方法**

- **离线和在线的区别**：离线一次性提交，测引擎极限吞吐；在线按速率到达，测给定压力下的用户体验。离线场景下的 TTFT 没有意义。
- **泊松到达**：平均速率固定，请求间隔服从指数分布，能模拟请求扎堆带来的排队。`--burstiness` 小于 1 更扎堆，大于 1 更均匀。
- **request-rate 和 max-concurrency**：前者是开环（不管服务处理得过来与否，按时发），后者是闭环（同时在途的请求数上限）。开环更能暴露过载时的延迟爆炸。
- **Little 定律**：系统中的平均请求数 = 到达率 × 平均延迟。可以用它检查压测结果是否自洽，也可以用来估算需要多大的并发容量。
- **为什么用 `--ignore-eos`**：两个引擎的数值不完全一致，自然结束的位置会不同，输出长度不同就不公平。
- **为什么要重复和看极差**：GPU 频率、CPU 调度、显存碎片都会带来噪声，单次 5% 以内的差异不可信。
- **为什么要 warmup**：首次运行包含 CUDA Graph 捕获、Triton 编译、显存分配，不代表稳态。

**精度评测**

- 非量化改动：贪心逐 token 对齐是最严格的标准。
- 量化改动：逐 token 对齐不适用，看下游任务精度（GSM8K、MMLU）或困惑度。
- 投机解码：理论上无损（贪心下输出完全一致，采样下分布一致），实际可能因为批形状不同的浮点误差在长序列后分叉，要能解释。
