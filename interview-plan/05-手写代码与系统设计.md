## 二、系统设计

### 答题框架

1. **澄清需求**：模型多大？QPS 多少？输入输出长度分布？延迟 SLO？有多少卡、什么卡？是对话、批处理还是 agent 场景？
2. **容量估算**：权重显存 → KV cache 每 token 大小 → 单卡能放多少 token → 结合 SLO 反推并发 → 需要几个实例。
3. **并行策略**：单卡放得下就优先 DP 多副本；放不下用 TP；MoE 考虑 EP；跨节点才考虑 PP。
4. **调度配置**：`max-num-seqs`、`max-num-batched-tokens`（chunked prefill 预算）、是否开 prefix caching、是否 PD 分离。
5. **优化手段**：量化、投机解码、KV 量化、cache-aware 路由。每一项说清收益和代价。
6. **验证方案**：怎么压测（场景、工具、指标）、怎么验精度、怎么监控。
7. **风险与降级**：过载时怎么办（限流、排队、降级到小模型）、长尾请求怎么处理。

### 例题 1：对话服务

> 用 Qwen3-30B-A3B 做一个对话服务，要求 TTFT < 1s、TPOT < 50ms，峰值 200 QPS，平均输入 1000 token、输出 300 token。你有若干台 A3。给出部署方案。

参考思路（自己先完整讲一遍再看）：

- 显存：BF16 权重 61GB，一个 die 放不下 → 至少 TP2；或者用 W8A8（31GB）单 die。
- KV：96KB/token。一次对话平均 1300 token ≈ 125MB。W8A8 单 die 剩约 30GB，可放约 240 个这样的请求。
- 并发估算：输出 300 token，TPOT 50ms → 单请求 decode 耗时约 15s。200 QPS × 15s = 3000 个并发在途。单 die 放不下，需要多实例。
- 再用实测的单实例 goodput 算实例数（这里就能引用项目 B 的数据）。
- MoE → 开 EP；decode 延迟敏感 → MC2；开 ACL Graph 的 `FULL_DECODE_ONLY`。
- 多轮对话有大量共享前缀 → 开 prefix caching + cache-aware 路由（按 session 做亲和）。
- TTFT 和 TPOT 互相冲突 → chunked prefill，预算从 8192 起调，用 goodput 当目标函数。
- 风险：热门专家负载不均 → EPLB；峰值超容量 → 排队 + 限流，宁可拒绝也不让 p99 爆掉。

### 例题 2：代码补全服务

> 代码补全：输入很长（整个文件，最多 8K token），输出很短（50 token），要求 TTFT < 300ms，延迟比吞吐重要。

要点：prefill 重、decode 轻 → 和例题 1 的权衡方向相反。prefix caching 收益极大（同一个文件反复补全）。n-gram 投机解码非常适合（代码重复多，这正好接到项目 A 的 S6 场景）。chunked prefill 的预算要大，因为 TTFT 优先。

### 例题 3：离线批处理

> 给 1000 万条数据做离线标注，只关心总成本和总时间。

要点：吞吐优先，延迟不重要 → batch 拉满、预算拉满、不开投机解码（高并发下负收益）。量化收益大。可以用更便宜的卡。按「每百万 token 成本」评估。

### 项目 A 的讲述骨架

> nano-vllm 是一个约 1400 行的最小推理引擎。我在它上面做了调度、KV cache 和投机解码三方面的优化，并用 vLLM 的标准压测工具，在同一张 4090 D 上和 vLLM 做了同口径对比。

重点讲三件事：

1. **hybrid 调度**：原版每步要么全 prefill 要么全 decode，长 prompt 进来会把正在 decode 的请求卡住，ITL p99 出现尖刺。我改成每步先给 decode 分配预算、剩余预算给 prefill 分块，和 vLLM V1 的 chunked prefill 思路一致。结果是 TTFT 和 ITL 同时改善。
2. **INT8 KV cache**：写入时量化、读取前反量化，KV 块数约 ×1.78，高并发下吞吐提升。精度用 GSM8K 验证（不能用逐 token 对齐，因为量化本来就会改变数值）。
3. **n-gram 投机解码**：在代码类数据上接受率高，并发 1 时 TPOT 明显下降；但并发升高后收益消失，因为那时 decode 已接近计算瓶颈。

**一定要主动讲的两件事**（这是加分项，不是减分项）：

- **decode pack 这一项没有可测收益**，差异落在噪声范围内，所以我不报加速比。小模型上 CPU 侧准备输入的开销占比太小。
- **我第一版的评测标准是自己设计的，口径和 vLLM 不一致，数字没法横向比**。后来重做成「给 nano-vllm 包一个 OpenAI 兼容服务，用 `vllm bench serve` 压两边」。这是我在这个项目里最大的收获：**性能结论的可信度首先取决于测量方法，而不是优化本身**。

### 项目 B 的讲述骨架

> 在 Atlas A3 上用 vllm-ascend 部署 Qwen3-30B-A3B，建立基线、剖析瓶颈，并做了一项优化。这个项目把上层引擎和底层算子串起来了。

重点讲：

1. 配置矩阵的对比结论（TP vs EP、图模式 vs eager、量化）。
2. 耗时拆解：decode 里 attention、MoE 计算、专家通信各占多少，瓶颈是什么。
3. **全链路追踪**：从 vLLM 的调度，到 vllm-ascend 选择 MoE 通信方式，到 `torch_npu` 的 dispatch / combine 算子，到 CANN 的 MC2 算子。这一段是你的差异化，要讲到「为什么 decode 用 MC2 而 prefill 用 AlltoAll」这个层次。
4. 优化项和原理。
