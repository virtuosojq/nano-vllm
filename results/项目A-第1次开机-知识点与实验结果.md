## 3. 实验结果

单位：吞吐为 req/s 或 tok/s；延迟为 ms。goodput = 同时满足 TTFT≤500ms 且 TPOT≤50ms 的请求吞吐。

### 3.1 饱和场景（rate=inf，goodput 几乎为 0 是预期）

t=0 打满时，TTFT 反映排队，**不要把 goodput=0 说成「达不到 SLO」**。这里只比饱和吞吐。

| 场景 | 指标 | nano 原版 | vLLM 对齐 | vLLM 默认 | nano / vLLM对齐 |
|---|---|---|---|---|---|
| S1 prefill 重 | req/s | 6.32 | **7.54** | 7.24 | 84% |
| S1 | output tok/s | 809 | 966 | 926 | 84% |
| S1 | total tok/s | 7279 | 8692 | 8338 | 84% |
| S1 | ITL p50 / p99 | 38.6 / 1231 | 25.6 / 515 | 26.7 / 163 | — |
| S2 decode 重 | output tok/s | 1672 | **3758** | — | **44%** |
| S2 | req/s | 1.63 | 3.67 | — | 44% |
| S2 | TPOT p50 | 111 | 46.7 | — | — |
| S4 共享前缀 | output tok/s | 2779 | **4029** | — | 69% |
| S4 | req/s | 21.7 | 31.5 | — | 69% |
| S4 | TTFT p50 | 3216 | 1705 | — | — |

读法：

- S1 最接近，nano 大约是 vLLM 的 84%。prefill 是计算密集，差距主要来自 kernel / 调度，不是 KV 容量。
- **S2 差距最大（不到一半）**：decode 是访存瓶颈，vLLM 的 CUDA Graph 分桶、attention backend、continuous batch 更成熟，batch 摊薄权重读取的效率更高。
- S4 nano 也慢一截。两边 prefix caching 都开，但 nano block size=256、vLLM 默认 16，命中粒度和 kernel 不同。S4 的 total tok/s 含大量前缀 token，头条仍看 output tok/s。

### 3.2 在线场景 S3（面试头条数字）

先看 inf 定容：

| | nano 原版 inf（300 prompts，约 4 req/s 那次） | vLLM 对齐 inf | vLLM 默认 inf |
|---|---|---|---|
| 饱和 req/s | 3.77（这次不是 inf 打满，是 ~4 rps） | 16.62 | **16.44 = R_max** |
| goodput | 3.76 | 0.22 | 0.16 |
| TTFT p50 | 52 | 2665 | 2567 |

vLLM inf 饱和 16.4 req/s，但 TTFT p50 已经 2.5s+，goodput≈0.16。  
**饱和吞吐远高于 SLO 可持续吞吐。** 这是可以单独讲的方法论点。

四档受控速率（同一组，每档 600 prompts）：

| 到达速率 | nano goodput | nano TTFT p99 | nano TPOT p50 | vLLM goodput | vLLM TTFT p99 | vLLM TPOT p50 |
|---|---|---|---|---|---|---|
| 4.11 | 3.91 | 653 | 16.9 | **4.00** | 94 | 11.4 |
| 8.22 | **7.26** | 122 | 25.4 | **7.56** | 112 | 13.7 |
| 12.33 | 1.81 | **11033** | 83.6 | **10.68** | 141 | 16.3 |
| 14.80 | 0.66 | **21582** | 98.1 | **12.32** | 175 | 18.7 |

结论（原版 nano vs 对齐 vLLM）：

- 大约 **8 req/s** 是 nano 原版的 SLO 拐点：8.22 仍接近打满到达速率，12.33 起排队爆炸。
- vLLM 在 **14.80** 仍几乎满 SLO（goodput 12.32 / 14.80 ≈ 83%，TTFT p99 175ms）。
- 在线口径下，nano 原版可持续 QPS 大约是 vLLM 的 **一半**。和 S2 的 decode 差距方向一致。
- 低负载（4.11）两侧 TTFT p50 都约 50ms，说明空载延迟接近；差距出现在高负载调度。

nano 在 4.11 的 TTFT p99=653ms 略超 500ms SLO，所以 goodput 3.91 < 4.11。值得记：平均看起来很好时，p99 已经在咬 SLO。

### 3.3 投机解码 S6（仅 vLLM，nano 下次开机）

数据集：`likaixin/InstructCoder`。n-gram：`num_speculative_tokens=4`，`prompt_lookup_max=3`，`prompt_lookup_min=1`。

| | conc=1 | conc=4 |
|---|---|---|
| req/s | 0.48 | 1.69 |
| output tok/s | 95.6 | 337.5 |
| TPOT p50 | **10.4 ms** | 11.4 ms |
| TTFT p50 / p99 | 25 / **65** | 30 / **1958** |
| goodput | 0.47 | 1.62 |
| draft 接受率（accepted/draft tokens） | 8.93% | 8.58% |
| 平均接受长度 | 1.36 | 1.34 |
| 各位置接受率 | 19.9% / 8.4% / 4.6% / 2.8% | 18.9% / 7.9% / 4.6% / 3.0% |

读法：

- 并发 1 时 TPOT 约 10ms，TTFT p99 很稳。
- 并发 4 时吞吐上去了，但 **TTFT p99 从 65ms 跳到 1958ms**，长尾被批形状 / 排队拉爆。
- 接受率偏低（首位 draft 只有 ~20%）。InstructCoder 没有「代码补全那种极高重复」，n-gram 在这个集上不是免费午餐。
- 计划里的判断仍然成立：**投机解码在低并发、访存瓶颈时值钱；并发升高后验证不再免费，长尾先坏。**

### 3.4 引擎内离线套件（旧口径，只作自我对照）

配置：`max_num_batched_tokens=16384`，`max_num_seqs=512`，prefill_priority。数字 **不能** 和 `vllm bench serve` 比。

| | 结果 |
|---|---|
| 正确性指纹 / 边界用例 | 通过，num_fail=0 |
| 离线吞吐（256 seqs） | **2273 tok/s** 完成 token |
| 延迟 batch=1 / 8 / 64 | 103 / 728 / 3832 tok/s |
| batch=1 TPOT | 9.6 ms |

旧口径在引擎 `step()` 后打点，不含 HTTP / 分词 / 流式。所以离线 2273 会高于 serving 口径的 S2 output tok/s 1672，这不是矛盾。

### 3.5 精度 GSM8K

协议：`lm-eval local-completions`，5-shot，greedy，`until=["Question:", "</s>", "<|im_end|>"]`，`num_concurrent=32`。  
数据：因 hf-mirror Hub API 429，改用本地 parquet（train 7473 / test 1319），任务 yaml 与官方 gsm8k 相同。

| | strict-match | flexible-extract |
|---|---|---|
| nano 原版 | **85.82% ± 0.96%** | 84.61% ± 0.99% |
| vLLM 对齐 | **84.99% ± 0.98%** | 84.61% ± 0.99% |

细节：

- 面试报 **strict-match**。flexible 两侧同分，是各错各的对消，不是逐条相同。
- 1319 条里 **446 条（33.8%）** greedy 原文不同，但 398 条抽出的最终数字仍相同；真正 pred 不同 48 条。kernel / batching 浮点差会导致贪心路径分叉，**不到 1 个点可以接受**。
- 两侧各 38 条没有 `####`，重叠 32 条，结尾是半截算式 → 默认 `max_gen_toks=256` 截断，不是 `stop` 失效（没有 `Question:` 泄漏，没有 `<think>`）。
- strict > flexible：`####` 抽对了，flexible 的「最后一个数字」regex 抽到了中间计算。过滤器噪音，不是服务 bug。
- 没有走 chat template，所以 Qwen3 的 thinking 模式没开。这是 **completions 5-shot 基线**，不要和官方 Instruct/thinking 榜单直接比。

## 4. 方法论知识点（这次实验专门练到的）

### 4.1 三种口径不要混

| 口径 | 打点位置 | 适合说什么 | 这次对应 |
|---|---|---|---|
| 引擎内部 | `step()` 之后 | 解释为什么快（prefix 命中、KV 利用率、n-gram 接受率） | `20261117_nano_4b_*.json` |
| 服务端 | HTTP 入口 | 含排队、注入等待 | nano_server 可打 |
| 客户端 | `vllm bench serve` | **和 vLLM 比的头条** | S1–S6 JSON |

旧评测的核心问题：离线套件从 t0 算 TTFT，测到的是排队；在线套件的到达时刻是 `add_request` 而不是泊松计划时刻。所以「ITL p99 从 5.07 降到 3.50」那种旧结论必须在新口径下作废重测。

### 4.2 inf 饱和 ≠ 线上能跑的 QPS

- `--request-rate inf`：所有请求在 t=0 注入，队列瞬间打满。
- 得到的 req/s 是 **系统最大排水量**。
- SLO goodput 是 **排水的同时还要满足延迟**。
- 本次：vLLM `R_max=16.44`，但 inf 时 goodput 只有 0.16；真正能对外承诺的是 12–15 req/s 这一档。

系统设计题里：先用 inf 估容量，再用 SLO 扫速率定实例数。这次就是这个流程的一次实操。

### 4.3 指标定义（背熟）

| 指标 | 含义 | 谁敏感 |
|---|---|---|
| TTFT | 首个输出 token 的等待 | prefill、排队、chunked prefill 预算 |
| TPOT | 每输出 token 平均时间（不含 TTFT） | decode 效率 |
| ITL | 相邻两个输出 token 的间隔 | 调度尖刺（长 prefill 卡住 decode） |
| E2EL | 端到端 | 总时长 |
| req/s | 完成请求速率 | 饱和容量 |
| output tok/s | 生成 token 速率 | decode 场景头条 |
| total tok/s | 含 prompt | prefill 重的场景会很大 |
| goodput | 满足 SLO 的 req/s | **在线服务头条** |

`ignore-eos`：压测强制生成固定长度，避免「模型爱说短话」造成吞吐虚高。精度评测不能加这个。

### 4.4 公平对比清单（被问「你怎么保证公平」时按条说）

1. 同一张卡，轮流跑，不同时占 GPU。  
2. 同一模型、同一 tokenizer 路径、同一 `--seed`。  
3. 同一客户端版本，同一 `--goodput` 阈值。  
4. `max_model_len / max_num_seqs / max_num_batched_tokens / gpu_memory_utilization` 显式对齐。  
5. 输出长度用 `--ignore-eos` 锁死。  
6. 另外保留「vLLM 开箱默认」组，回答「和用户直接 `vllm serve` 比怎么样」。  
7. 精度单独用 greedy + 固定 stop，不和压测混。

本次未完全做到的：S1/S3 三次中位数；S3 `num-prompts=rate×150`；block size 无法对齐（nano 256 vs vLLM 16），报告里必须注明。

## 5. 原理知识点（用这次的数字当例子）

### 5.1 Prefill vs Decode

| | Prefill | Decode |
|---|---|---|
| 计算 | GEMM，算力瓶颈 | GEMV，访存瓶颈 |
| 对应场景 | S1、S3 里的长 prompt | S2、S3 的稳态生成 |
| 本次 | S1 nano≈vLLM 的 84% | S2 nano 只有 44% |

batch 从 1 增到 64，引擎内 tok/s 从 103 到 3832，因为权重只读一次、被序列摊薄。这就是 continuous batching 有效的原因。

Qwen3-4B 权重约 8GB BF16。decode 时间下限 ≈ 权重字节 / 显存带宽。实测远高于下限时，瓶颈在 kernel 启动、调度、或 batch 不够大。

### 5.2 KV cache

```
每 token 字节 = 2 × layers × kv_heads × head_dim × dtype_bytes
Qwen3-4B: 2 × 36 × 8 × 128 × 2 = 147456 B ≈ 144 KB/token（BF16）
```

vLLM 对齐组 KV 约 12.33 GiB → 大约能存 `12.33GiB / 144KB ≈ 9 万 token`。  
`max_num_seqs=256`、`max_model_len=4096` 的理论上限是 256×4096，远大于物理 KV，所以真正限制并发的是 KV 容量，不是 seq 配置。INT8 KV 的故事下次开机再补数字（预期块数约 ×1.78）。

PagedAttention：KV 按块分配。nano block=256，vLLM=16。大块：block table 短、kernel 更整齐，前缀命中粒度粗；小块相反。S4 的对比必须带上这句。

### 5.3 调度：prefill_priority vs chunked prefill / hybrid

nano 原版：**一步要么 prefill、要么 decode**。新请求一来，正在 decode 的序列被整步打断 → ITL p99 尖刺。S1 ITL p99=1231ms、S3 过载后 TTFT p99 到 10s+，都是队列和「prefill 独占」叠加。

vLLM V1：chunked prefill，每步有 token 预算 8192，decode 和 prefill 分块可以同一步。这是 S3 高速率下 vLLM 仍能压住 TTFT 的主因之一。

下次开机要验证的对应关系：

| nano 变体 | 对应 vLLM 思想 | 预期 |
|---|---|---|
| token_budget | 限制每步 prefill token | ITL p99 降，TTFT 升 |
| hybrid | decode 先占预算，剩余给 prefill | TTFT 和 ITL 同时改善，S3 goodput 升 |
| 原版 prefill_priority | 无 chunked | 本次基线 |

### 5.4 Prefix caching

满块哈希（内容 + 父块哈希）命中则跳过 prefill。S4 给了 1024 的共享前缀（256 的倍数，兼容 nano 块大小）。  
随机数据几乎不命中，所以 S1/S2 开不开 prefix 影响不大；前缀场景要单独测。

### 5.5 投机解码

decode 访存瓶颈 → 一次验证 k 个 token 的前向成本和算 1 个接近。n-gram 从 prompt / 已生成文本找重复，draft 成本≈0。

无损：贪心时逐 token 比对，不一致就截断；采样时用拒绝采样。工程上批形状不同会有浮点差，GSM8K 里 33% 原文不同就是同类现象。

盈亏：接受率低或并发高（已经偏计算瓶颈）时，验证变贵。本次 conc=4 的 TTFT p99 已经先坏，接受率也只有 ~9%。

### 5.6 OpenAI 服务实现里真正影响数字的点

- **只有引擎线程调 `engine.*`**，HTTP 侧只往队列丢请求。  
- 每步推增量，不能攒完再发，否则客户端 TTFT/ITL 全错。  
- `stop` 命中后要截断 **并通知引擎停这个序列**，否则会生成到 `max_tokens`，GSM8K 又慢又脏。本次 stop 已验证生效。  
- 最后一个 SSE chunk 要带 `usage`，否则客户端会重新分词，token 数和真实生成对不上。  
- `prompt + max_tokens > max_model_len` 应返回 400，不要静默截断。

### 5.7 Attention 相关（环境里实际用到的）

两边 attention 都是 FlashAttention v2，不是 flashinfer attention。  
vLLM 的 flashinfer **sampler** JIT 在这台机器上编不过（见下一节），与头条吞吐关系不大，因为 bench 是 greedy。

FlashAttention 减少的是 HBM 读写，不是 FLOPs。online softmax 保证分块结果等价。

## 6. 环境与工程判断（也可以当项目里的「坑」讲）

讲这些是为了证明你能把引擎跑起来，不是为了抱怨环境。挑 2 条面试说即可。

1. **CUDA 13 wheel vs 系统 CUDA 12.4**：torch 2.13+cu130 能跑（驱动 580 支持），但 flashinfer JIT 调用 `nvcc --compress-mode=size` 失败。处理：`VLLM_USE_FLASHINFER_SAMPLER=0`。Attention 已是 FLASH_ATTN。  
2. **EngineCore 子进程 PATH 没有 ninja**：venv 里有二进制，父进程没 export。JIT 编译直接挂。  
3. **`eval $(vllm_cmd)` 拆 JSON**：`--speculative-config '{"method":"ngram",...}'` 被拆成非法参数。改成 bash 数组直接 exec。  
4. **进程收不干净**：SIGTERM 杀不掉 EngineCore，tee 卡住；失败脚本的 vLLM 会被 reparent 到 pid 1，占端口不占显存。固定动作：`pkill -f vllm.entrypoints; pkill -f EngineCore; pkill -f bench.nano_server`。  
5. **客户端和服务器不能共用 `CUDA_VISIBLE_DEVICES=""` 的 wrapper。**  
6. **Hub 限流**：hf-mirror API 429，resolve 下 parquet 仍可用。数据集要有本地副本。  
7. **`lm-eval[api]`**：`local-completions` 依赖 tenacity/aiohttp，只装 `lm-eval` 不够。

## 7. 项目讲述骨架（填进 `05` 的模板）

**【一句话】**  
给 nano-vllm 做了可被 vLLM 官方工具压测的 serving 层，在 4090 D / Qwen3-4B 上拿到和 vLLM 0.31 同口径的基线：在线 SLO 可持续吞吐大约差一半，GSM8K 精度齐平。

**【背景】**  
第一版评测在引擎进程内打点，和 vLLM 客户端数字不能比；离线 TTFT 是排队。要投推理引擎岗位，必须先把测量做对。

**【我做了什么】**（当前只能讲到基线；优化项等第二次开机补数字）

1. OpenAI 兼容服务：流式增量、stop 截断并 abort 序列、usage。原理：客户端测的 TTFT/ITL 完全依赖「每步是否真的把新 token 推出去」。  
2. 场景矩阵 + 同一客户端。原理：inf 看容量，受控到达 + goodput 看线上。  
3. 对齐配置 vs 默认配置分开报。原理：vLLM 默认 max_model_len=40960，和 nano 的 4096 不是同一个 KV 预算。

**【怎么验证】**  
`vllm bench serve`；ShareGPT / random / InstructCoder；GSM8K 5-shot；单元测试 + 引擎内 correctness。单次跑，未做三次中位数，极差未知。

**【结果】**  
见第 3 节表。一句话：空载延迟接近，高负载 decode 和在线 goodput 差一倍，精度差 <1 个点。

**【没做成 / 代价】**  
- 优化变体还没在新口径下重测。  
- S0 0.6B 环境一致性没复现。  
- 256 gen tokens 截断了约 3% 的 GSM8K。  
- n-gram 只测了 vLLM，接受率偏低。  
- flashinfer sampler 被迫关掉。

**【学到了什么】**  
1. 测量方法和优化本身一样重要。  
2. 报加速比之前先问：这是饱和吞吐还是 SLO 可持续吞吐。

## 8. 面试追问（结合本次数据的答法）

**Q：为什么 S1 goodput 是 0，系统是不是坏了？**  
A：inf 在 t=0 打入 1000 条 1024-token 请求，TTFT 变成排队时间，必然超 500ms。看 req/s 和 tok/s。SLO 要看 S3 受控到达。

**Q：为什么 S2 差得比 S1 多？**  
A：S2 是 decode 访存瓶颈。vLLM 的 Graph 分桶、kernel、异步调度让大 batch decode 更接近带宽上限；nano 原版一步不能混 batch，还有 Python 调度开销。S1 是 GEMM，差距被算力盖住。

**Q：8 req/s 和 15 req/s 对线上意味着什么？**  
A：同样的 SLO，nano 原版大约要 2 倍实例数。优化目标就是把 S3 拐点往 vLLM 那边推（hybrid + INT8 KV）。

**Q：GSM8K 贪心为什么 1/3 原文不同？**  
A：不同 kernel、不同 batch 形状 → 浮点累加顺序不同 → greedy argmax 在 logits 接近时分叉。抽出的最终数字大部分仍相同，strict 只差 0.8 个点。投机解码「长序列后分叉」是同一类问题。

**Q：block size 16 vs 256 公平吗？**  
A：不完全公平。这是实现约束。前缀长度取 256 倍数减轻粒度差。不把 S4 的倍数差说成「纯算法优势」。

**Q：R_max 为什么不用 nano 的 inf？**  
A：速率网格必须两侧相同才能比 goodput。用更强的一边定网格，弱的一边会在高档掉队，这正是我们要看到的拐点。
